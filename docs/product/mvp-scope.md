# MVP 范围与会议调整

版本 0.3；2026-10-14。项目管理为主、设计为辅；**先在方案相关部门跑通管理闭环，成熟后扩展**，替代 0.1 版两个业务场景同时试点的建议。依据见[会议复核](../meetings/2026-10-14/review.md)与[文字差异复核](../meetings/2026-10-14/text-comparison.md)。本次补全权限、提醒、改期警示及评价口径；具体实现、技术和安全细则仍待确认，本轮仅更新文档。

## 最小业务闭环

业务/经营人员明确需求、期限和成果要求 → 分派至项目节点与技术人员 → 日常提醒和反馈 → 提交成果、登记质量意见 → 部门/项目负责人确认 → 甲方修改形成新节点，必要时个人申请改期、管理人员调整 → 核心管理人员查看异常、过程证据与项目摘要。

会议希望项目群与核心管理范围衔接这一过程；自动取得群消息属于待验证条件，不可写成已经具备的企微接口能力。

## 群协同的两条待评审路径

**路径 A：自动关联授权群信息。** 核验公司群类型、消息/文件取得途径、实际 API 能力及成员授权后，再评估归类、节点关联、定向通知与管理汇总。每条信息属于哪个项目、可给谁看都须可追溯，不默认拥有普通群全量记录或私人微信读取权。

**路径 B：应用内提交，授权渠道通知，管理端汇总。** 若 A 不可行，用明确的提交入口收集成果与反馈，再通知相关人员。可以验证闭环，但不能称为已自动读取原有群聊。这是备用提案，需 D114 明确接受，不能默认替代公司期望。

AI 提取节点或归类可以先生成待确认建议；自动写入的权限和确认机制尚未批准。会议没有授权任意自然语言派单、改期或审批。

## 方案节点与改期

总项目下有节点，甲方修改形成新的跟进节点/指引并关联原成果。“小项目”是业务表达，不直接锁定无限递归项目树或数据库表。实际活动、节点层级、审核岗位和终审人由 D103、D115 细化。

成果提交不自动等于负责人确认；是否另有甲方确认须分清。不同节点不必都上传文件，按明确交付要求处理；文件链接也要验证访问权和版本可定位。

会议提出个人申请改期、管理人员调整，因此最小申请/处理记录纳入 M02；复杂审批平台仍后置。需要改期的情境下，未申请或未获同意仍要警示（E18）；待定的是触发时点、申请待处理期间行为、批准人和等待甲方/休假是否停钟。建议保留原期限、理由、处理者、新期限；未批准不能自行抹去原期限。

每日提醒和到期前一天反馈/预警已有口径（E17）；“今天提交”仍须明确提交内容，不能把所有正式截止日期提前一天。指定核心管理人员可包括经理与高层；S1 的逐级升级与会议共同提醒应以事件—接收人—时点表协调，不能默认全部先由 PM 处理。

## AI 与评价

首版 AI 是明确偏好，应围绕收集反馈、信息归类、过程检索和问题解释设计，以结构化事实及证据为基础。若模型许可或接口条件不足，需要明确评审首版调整，不能把完全无 AI 当作公司已经接受的最终交付。

人工评价与自动绩效处分分开。会议已明确未评价按零分、不奖不扣；在计分语义中贡献为 0，同时保留“未评价”状态，与“已评价为良好、得 0 分”区别，不能据零分推断已确认完成。会议提出优 +1、不及格 -1、良好 0 的初步方案；“优良中差”的完整对应、评价人、汇总/纠错及首版是否计分仍待 D113 补齐。建议 M10 保留“结论 + 意见 + 证据 + 评价状态/历史”，首版计分范围明确后再定数值功能；不再把未评价含义列为完全未知。

## 推荐推进顺序

1. 将会议方向写成规格草案，补齐具体试点/终审人、群边界、提醒改期参数、权限数据清单和评价首版范围。
2. 经授权后用虚构数据验证任务—反馈—成果—改期—异常—摘要，分别核对业务、技术和管理视角。
3. 获得测试企微授权后验证身份、消息/群信息路径、文件权限和失败场景，决定 M09 的实现范围。
4. 方案部门 UAT 检查延期/质量/变更是否可追溯，记录人工追问成本与误报。
5. 单独决定上线和推广。技术栈、数据政策、运行责任仍未定，不承诺旧计划周数。
