# 技术方案候选与取舍

版本 0.3；2026-10-14，根据会议及用户整理文字补充约束，未作选型。企业微信自建应用方向已明确，用户承担技术；以下候选仍非公司批准架构，不安装框架、不生成应用骨架、不配置云资源。

## 先确认现有系统是否可复用

MN01 L9–L13 明确公司说明已有服务器、数据库和进度表，表由“小宝”掌握（E15）；具体产品、版本、接口、维护岗位和访问条件尚未盘点。若现有系统具备项目、任务、文件权限和审计接口，可评估复用，减少重复台账；代价是依赖 API、许可和变更能力。若不能满足再评审独立后端。存在设施不等于可直接集成，不能直接决定全部重建（D102、D111）。

## 自建情况下的候选

| 事项 | 候选及理由 | 替代方案与代价 | 决策前提 |
| --- | --- | --- | --- |
| 架构组织 | 模块化单体作为首版评审起点，项目/任务/权限/通知职责分开，降低多服务协调负担 | 扩展现有系统；微服务仅在团队、部署隔离或规模有证据支持时评估 | 系统现状、团队与运维能力 |
| 后端 | TypeScript + NestJS：若团队熟 TS，可利用其模块化结构统一应用约定 | Python + FastAPI：若团队熟 Python，可围绕类型与 API 开发；两者都仍需业务授权、审计和任务可靠性设计 | 团队技能、公司标准、维护人 |
| 数据 | 关系型数据库作为候选，便于项目关系、状态与审计一致性；PostgreSQL 为旧计划中的可评审项 | 复用公司既有合适数据库；本地原型存储只能验证流程，不能代表生产可靠性 | 现有设施、数据政策、备份恢复和容量 |
| 任务与通知 | 持久化待发送记录 + 调度机制；规则、业务事件和结果可追踪 | 数据库任务表/现有调度设施，或 Redis + BullMQ 等专用队列；后者引入额外服务运维，不能仅为定时器就默认上齐 | 发送量、失败恢复目标、可用运维 |
| 前端 | 优先评审移动端任务表单、PM 队列与管理摘要，页面形式以企微测试验证为准 | 复用公司前端体系；React、Next.js 是旧计划候选，不将完整框架作为默认必要条件 | 前端技能、企微实际能力、页面需求 |
| 文件 | 已有受控文件系统的版本引用可作为轻量起点，前提是访问权及历史版本可验证 | 应用受控上传/对象存储更统一，但要补类型/大小限制、恶意文件处理、存储策略和访问校验 | D107、D108 |
| AI | 结构化事实查询 + 有来源的只读表达；未批准模型处理时保留规则式摘要 | 经批准的云模型、私有模型或暂不启用模型；不能仅凭性能忽略成本和数据边界 | D108、D110 |

NestJS 的 TypeScript 与应用架构定位见 [NestJS 官方介绍](https://docs.nestjs.com/)；FastAPI 的 Python API 定位见 [FastAPI 官方文档](https://fastapi.tiangolo.com/)；PostgreSQL 的关系型数据能力见 [PostgreSQL 官方介绍](https://www.postgresql.org/about/)。资料于 2026-10-09 查阅，仅支持候选能力描述。对本项目的适用性是上述条件下的工程判断，不是官方对本项目的背书；未锁定版本、ORM、队列、前端或托管商。

## 安全与业务制度必须单独决定

| 未决事项 | 需要公司提供的决定 | 批准前可继续的工作 |
| --- | --- | --- |
| 授权范围 | 角色/项目/动作/文件/导出权限及授权管理者 | 梳理权限矩阵模板和越权测试样例 |
| 数据处理 | 数据分类、模型可接收字段、地区、存储/日志留存、备份/恢复责任 | 使用虚构数据讨论流程，不上传真实材料 |
| 企业微信 | 测试应用和账号、管理员、允许接口、回调/身份/通知约束 | 只编写可行性验证清单；本轮不执行接入 |
| 督办制度 | 阈值、日历、静默期、升级路径、外部等待和人工覆盖 | 参数化验收案例，具体数值保持未定 |

前往 `$speckit-plan` 前需要可执行的公司答案，而不是让工具为了填满模板自行选择。关于安全数据地区等不提供法律结论；由公司指定责任人完成相应审查。
