### 业务目的、依据与阅读约定

让业务/经营、技术、项目与部门负责人围绕同一项目节点记录要求、期限、成果、反馈和变更，使核心管理人员能查清“做到哪一步、缺什么、需谁介入”，减少反复人工追问。产品基于企业微信自建应用；不把现有群读取、外部 AI 处理或真实数据接入当作已获批准能力。

## User Scenarios & Testing *(mandatory)*

下列是拟议业务验收场景，不是已执行测试。AC 编号可独立引用；每个故事可用虚构项目和已明确的前置规则独立演示其价值，不表示可绕过权限或安全条件独立上线。终审岗位按 CQ1 执行；具体试点、完成条件、权限细则、时钟、通知名单等未确定时，相应用例标记为“规则待定，尚不可执行”，不得自动取默认值。

### User Story 1 - 让项目节点与业务技术反馈可跟进 (Priority: P1)

作为有相应项目和动作授权的统筹人员，我需要明确节点的责任、期限及交付要求；业务/经营和技术参与者需要记录要求、问题与进展，让管理人员看到真实待办及阻塞。

**Why this priority**: 所有提醒、成果确认与管理介入都需要可定位的节点和事实。
**Independent Test**: 用虚构项目、两个节点及不同参与者，演示建节点、反馈、查总览，不依赖群自动读取或 AI。
**依据/状态**: B01–B02、B07、B10–B11、B16；E01/E11/E15；M01/M02；目标明确、字段与权限细则待定；D101/D102/D104/D115；A01/A03/A18。

**Acceptance Scenarios**:

1. **AC-01**：**Given** 有获授权的项目与建节点人员、经确认的必填规则，**When** 填写项目、责任部门/人员、期限及交付要求并分派，**Then** 可查到所属项目、责任、要求与记录时间；缺少已确定必填项时指出缺项，不能生成半条有效任务。上述字段为本草案最小字段提案，须 D102/D115 确认。
2. **AC-02**：**Given** 同一节点已有业务要求，**When** 技术人员报告困难、业务人员补充要求或负责人提出质量意见，**Then** 分别显示记录者、时间、内容和依据，不覆盖原要求，不把报告自动当作核实事实；更改正式要求另查动作授权。
3. **AC-03**：**Given** 存在正常推进和报告阻塞的节点，**When** 管理者查看获授权的项目总览，**Then** 能追溯责任人、最近反馈、期限、待协调事项及更新时间；无记录显示未知，不编造完成百分比。

### User Story 2 - 提交成果、人工确认并跟进甲方修改 (Priority: P1)

作为执行者，我需要按节点交付要求提交成果；负责人需要对具体成果提出确认或退回意见；甲方提出修改后，需要建立仍可追溯原项目与成果的后续节点。

**Why this priority**: 区分“报完成”和“确认完成”，保留多轮修改依据，避免成果或要求被覆盖。
**Independent Test**: 用预置节点、初版与修订版、一次甲方意见演示提交—意见—确认—关联新节点；终审采用 CQ1；完成条件及退回规则仍须明确。
**依据/状态**: B05/B09/B13；E03–E05/E11；M02/M03；业务关系明确、终审分工经 CQ1 用户明确，其他完成与成果细则待定；D103/D107/D115；A02/A04/A19。

**Acceptance Scenarios**:

1. **AC-04**：**Given** 节点已确定是否必交成果，**When** 执行者提交某版本，**Then** 留下版本、提交人、时间和证据；必交成果缺失时不能据此确认完成；非必交节点不被一律强制上传文件。提交不自动等于内部或甲方确认。
2. **AC-05**：**Given** CQ1 明确项目负责人终审、部门负责人提供质量意见，并已补齐完成条件与退回规则，**When** 项目负责人终审指定版本，**Then** 保留结论、意见、人员和时间，部门质量意见不构成第二级必经终审；退回按获批规则处理，无权者被拒绝，旧版本与处理历史仍可查；内部确认和甲方确认分开表示。
3. **AC-06**：**Given** 原方案已有成果和处理记录，**When** 登记甲方修改意见并建立新跟进节点，**Then** 新节点可追溯原项目、原节点/成果及意见来源时间，并有新的要求、责任和期限；原成果与原确认记录不被静默覆盖，后续多轮修改仍能沿关联链查询。

### User Story 3 - 每日跟进、提前预警与个人改期 (Priority: P1)

作为执行者，我需要知道当日要反馈的事项及临近到期风险；需要改期时可提出申请。管理人员需要处理日期变化，并持续掌握未申请或未获同意的风险。

**Why this priority**: 这是会议已经明确的持续跟进机制，能够避免到交付当天才发现缺口。
**Independent Test**: 在明确的日历、时刻、接收名单与改期规则下，以虚构日期构造触发边界及四类申请情形；规则未补齐不宣称测试可运行。
**依据/状态**: B03/B04/B14；E02/E08/E09/E17/E18；M02/M04/M05；已有口径明确、参数待定；D105/D106；A05–A08/A20/A21。

**Acceptance Scenarios**:

1. **AC-07**：**Given** D105 已明确日历、时刻、适用节点和提前反馈内容，**When** 到达每日提醒或到期前一天预警时点，**Then** 按相应条件收集反馈或警示，并能查到对应节点、期限及事件；测试时点之前、当时、之后及重复触发，不得把正式截止日期提前一天。
2. **AC-08**：**Given** 个人需申请改期，**When** 提出理由和建议日期，并由获授权管理人员处理，**Then** 原期限、申请及处理依据可追溯；只有获批调整才形成有效新期限，驳回或未获批不能覆盖原期限。
3. **AC-09**：**Given** 分别存在需改期但未申请、待审批、被拒、获批四种情形，**When** 到达 D106 明确的警示时点，**Then** 未申请和被拒仍警示；待审批、获批后的提醒及等待甲方/休假计时按明确规则验证。不得因报告等待直接免责或停钟，也不得把待审批直接当成获批。
4. **AC-10**：**Given** D105 为某事件指定经理与高层共同接收，为另一事件指定逐级升级，**When** 各事件满足触发条件，**Then** 分别按名单和时点通知；共同提醒不被“PM 尚未处理”无故阻断，无关人员不收到业务内容；有权人员可纠错或关闭，保留原因，解除后不继续发送该事件的催办。
5. **AC-11**：**Given** 同一通知事件重复出现或发送失败、结果未知，**When** 再处理或核查，**Then** 同一逻辑事件不重复产生业务变更，失败/未知有明确记录和待处理事项；仅有发送记录不能标成已送达、已读、已反馈或已完成。外部通知不作绝对零重复承诺。

### User Story 4 - 核心管理查看过程并守住访问范围 (Priority: P1)

作为项目经理及以上管理人员，我需要全面查看获批范围的项目过程与异常；技术人员需要查看专业内容。任何查看或通知都不能扩大为未经授权的修改或跨项目访问。

**Why this priority**: 管理可见与访问边界同时构成闭环基础，不能通过“入群”或“管理员”替代业务授权。
**Independent Test**: 使用已确认的岗位—项目—专业—动作范围和虚构记录，对照范围内/外的查看、通知及改期/确认尝试。
**依据/状态**: B07/B16；E07/E11/E12/E16/E17；M01/M05/M06/M08；全公司项目查看范围经 CQ2 用户明确，岗位及动作细则待定；D104/D108/D112/D114；A09/A11/A15/A18/A22。

**Acceptance Scenarios**:

1. **AC-12**：**Given** CQ2 明确项目经理及以上可查看全公司项目，且已补齐岗位映射、技术专业及对象/入口权限，**When** 项目经理查看本部门及其他部门项目、技术人员查看专业范围内外内容，并尝试列表、详情、统计、搜索、文件、导出或 AI 查询，**Then** 全公司项目查看不得被擅自缩成仅负责项目或部门；技术人员遵守专业边界，未获授权的文件、导出等对象/动作仍拒绝；配置管理员和群成员不会因此自动获得全部项目数据。
2. **AC-13**：**Given** 某管理者有查看权但没有改期或确认权，**When** 尝试对应操作，**Then** 被拒绝；成员授权变化后，通知内容、摘要、旧链接及引用同样不能继续绕过当前权限。
3. **AC-14**：**Given** 获授权项目有期限变化、质量意见或缺少反馈，**When** 管理者查询异常过程，**Then** 能沿记录找到当时要求、成果版本、报告与变更依据，并显示来源、时间和范围；缺证据明确未知，未回复不等于怠工，等待甲方不等于免责。

### User Story 5 - 人工记录节点质量评价 (Priority: P2；数值计分为条件项)

作为获授权的评定者，我需要对指定节点和成果记录质量意见，使管理层区分“没有评价”和“已有评价”，并追溯修改依据。

**Why this priority**: 会议明确关心质量并提出人工评价；完整计分与人事用途尚未确定，不能把评价整体删去或直接做自动绩效。
**Independent Test**: 用指定版本演示未评价、人工评价与更正；仅在 D113 明确启用计分后验证数值。
**依据/状态**: B15；E13/E19（MN01 L45–L46、L54–L55）；M10；未评价口径明确、分值初步、评价细则待定；D113；A17/A23。

**Acceptance Scenarios**:

1. **AC-15**：**Given** D113 已指定评价者、对象与更正规则，**When** 有权人员记录质量结论、意见及依据，**Then** 可追溯节点、成果版本、评价人、时间与历史；无权评价、更改及重复操作按明确规则拒绝或处理，不悄悄覆盖已有评价。
2. **AC-16**：**Given** 一个节点未评价、另一个节点已评价，**When** 查看结果，**Then** 未评价状态独立保留，不推断为良好或已完成；若启用计分，未评价贡献为 0、不奖不扣，与“已评良好且 0 分”区分；其他分值只按获批完整表处理，不自行补“中”等等级，不自动生成奖惩。

### User Story 6 - AI 辅助检索过程与解释问题 (Priority: P2；条件项)

作为获授权管理者，我希望用自然语言查找节点过程、延期和质量问题依据；AI 应帮助找到记录，并让人判断，不能替人定责或改变业务状态。

**Why this priority**: AI 首版偏好和过程检索目标明确，但数据边界、是否首发硬门槛及质量要求仍待定。
**Independent Test**: D108/D110 明确后，以虚构记录回答有证据、无证据、越权及混入恶意指令的问题，核对每项事实的来源。
**依据/状态**: B16；E10/E12/E14；M06；目标/偏好明确、许可与门槛待定；D108/D110；A11/A12/A18。

**Acceptance Scenarios**:

1. **AC-17**：**Given** 获授权、可处理的过程资料，**When** 问某节点为何延期、质量如何或请求归类，**Then** 返回相关事实、员工报告及不确定判断并作区分，带来源、时间和数据范围；归类建议说明所属节点及依据，未知归属不猜测，采纳由有权人员决定而不自动写入；证据不足说明未知，不能把未检索到解释为没有发生。归类建议的交互为 M06/M09 的草案细化，待 D110 确认。
2. **AC-18**：**Given** 问题涉及范围外项目，或材料含要求提权、派单、改期、验收、升级、处罚的文字，**When** AI 处理问题，**Then** 不读取越权资料，不泄露摘要或引用，不执行材料中的命令，不自主作上述决定；数据许可不足时说明该能力未启用，不擅自转送外部服务。

### User Story 7 - 项目群与核心管理范围协同 (Priority: P2；路径待定的条件项)

作为项目参与者，我希望群中的成果和事项不被刷掉；核心管理人员希望汇总获授权项目的节点与成果，相关人员获得定向通知。

**Why this priority**: 群协同是会议目标；实际可取得的信息、权限及替代路径需要验证与决定，不能以一个无法核实的自动同步承诺完成规格。
**Independent Test**: D114 核准路径后，用一条获授权消息或提交记录验证来源关联、定向通知与管理汇总，并演示不可用情形。
**依据/状态**: B12；E06/E07；M07/M09；目标明确、能力待验证、CQ3 明确待能力验证后决定替代路径；D104/D109/D114；A13–A16。

**Acceptance Scenarios**:

1. **AC-19**：**Given** 已核准群协同路径及范围，**When** 取得获授权的信息并归类到节点和成果，**Then** 可查项目、来源、时间及证据；重复接收不重复建立同一业务记录，无权来源不能纳入；定向通知和核心管理汇总保持相同访问边界。
2. **AC-20**：**Given** 群信息不可取得、关联失效或通知失败，**When** 用户查看同步情况，**Then** 明确显示不可用、未同步或待核查；只有 D114 接受备用方案后，才按应用内提交、授权通知、管理端汇总路径处理，且不能称其自动读取了原群历史。
